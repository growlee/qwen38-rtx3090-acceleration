Итого: 1400 оценённых ответов на общей 200-task выборке, исключая warmup;
отдельные 200 исторических координат BLOCKED из-за отсутствующих точных весов/

60 × 3 сохранена отдельно и в эти баллы не объединена.

Weighted decode = сумма completion tokens / сумма измеренных decode seconds.
Это не полное время ответа и не медиана старого 1024-token benchmark. Сравнение
межсессионное, без статистических повторов; строгое оформление ответа влияет
на PASS. Это адаптированный скрининг, не официальный HumanEval score и не
многошаговый coding-agent. GGUF тоже квантован: BF16-oracle здесь отсутствует.

## Вывод по качеству и ресурсам

- DFlash fast и INT8 имеют ровно тот же набор PASS/FAIL, что AutoRound.
  DFlash fast — приоритетный кандидат для выделенного LLM-профиля по этой
  выборке; пик VRAM 23860 MiB оставляет мало места другим GPU-процессам.
  INT8 экономнее: пик 21904 MiB. Это рекомендации, не переключение production.
- Huge добавил три критических провала относительно AutoRound/fast, включая
  retrieval и два вырожденных ответа с повтором `Register`. Пик 24122 MiB.
  Причина не локализована; нельзя приписывать её одному KV или размеру окна.
- Новая калибровка Adaptive не обосновала замену рабочего варианта: тот же
  общий балл, новый RU-провал и исправление строгого `Казань`/`Kazan` случая.
  Небольшой выигрыш decode 1,47% не доказан как воспроизводимый.
- У быстрых вариантов сохраняются критические регрессии относительно GGUF.
  «Без потерь вообще» и универсальное превосходство не доказаны.

## Контекст: измеренное отдельно от настроенного

**Максимальный фактический prompt — 11017 токенов. Полезные 32k/50k/200k
не проверены.** Числа последнего столбца — использованные лимиты профилей,
не доказанная полезная длина и не предельные возможности каждого формата.

Read-only снимок Server A от 2026-09-08, 12:20–12:23 UTC:
backend `/v1/models` подтвердил `max_model_len=57344` у рабочего Adaptive;
CTX fast, MTP k4, BF16 KV, GPU_UTIL .93, PREFIX_CACHE 0. Qwen/gateway/Open WebUI
были healthy. Это датированное наблюдение, не новое измерение при записи сводки.

Общий контекст включает оформленный вход и выход. При резерве 4096 токенов
на ответ остаётся 53248 на вход, включая system/history/tools/chat template.
`max_position_embeddings=262144` в target config не отменяет лимит runtime.
Live startup показал KV pool 73617 токенов / 5,35 GiB; это не лимит одного API-запроса.

Расчёт BF16 KV по архитектуре: 16 full-attention слоёв × 2 (K,V) × 4 KV-heads ×
256 head_dim × 2 байта = 65536 байт/токен. Для 200000 токенов это 12,21 GiB
только плотного KV; вместе с измеренными weights + non-torch 14,32 GiB уже
больше 24 GiB. Это оценка без остальных состояний/workspaces, не benchmark.
Просто увеличить MAX_LEN до 200k в текущем профиле недостаточно.

В установленном скрипте есть ещё не квалифицированные на наших весах ветки:
MTP long = 150000 / FP8 KV / k3; MTP huge = 200000 / KVarN K4/V2 / k3;
DFlash long/n7 = 131072 / INT8 per-token-head KV / Triton. Они не получают
автоматически результаты fast. У развернутого gateway также подтверждён
предел тела запроса 1048576 байт JSON; это не число токенов и отдельный риск
для длинного пользовательского запроса. Лимит не менялся.

Следующий предложенный этап — конечная 32k/50k серия на существующих fast
профилях, затем 128–150k с другим KV, затем отдельная квалификация 200k.
Ни один из этих этапов ещё не выполнен. Проверка контекста не управляла
скачиванием FreeToken и не оценивала его прогресс.
